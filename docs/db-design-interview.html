01正規化とは

一言でいうと「同じ事実を、2箇所に書かないようにテーブルを分けること」。

定義

正規化 = 1つの事実（ファクト）を1箇所だけに保存するように、テーブルを分解していく作業。目的は「きれいにすること」ではなく、更新時にデータが矛盾しないようにすること。

正規化しないと何が起きるか（アノマリー）

種類起きること例
更新同じ事実の片方だけ直して食い違うユーザー名を users と posts の両方に持たせると、改名したとき片方だけ古い
挿入まだ存在しない対象の情報を入れられない「部屋」と「対戦結果」を1テーブルにすると、対戦前の部屋を作るのに結果列が埋められない
削除1行消すと別の事実まで消える最後のメッセージを消したら部屋の情報まで消える

第1〜第3正規形

段階ルール違反の例直し方
1NF 1つのセルに1つの値だけ。繰り返し・配列・カンマ区切りを入れない used_theme_ids integer[]、"a,b,c" のような文字列 room_used_themes(room_id, theme_id) の行に分ける
2NF 複合主キーの一部だけで決まる列を外に出す (room_id, user_id) が主キーの表に user_name（user_idだけで決まる） users に持たせ、参照する
3NF 主キー以外の列から決まる列（推移的依存）を外に出す orders に customer_id と customer_name を両方持つ customers を参照する

非正規化は「間違い」ではなく「取引」

正規化すると結合が増えて遅くなる。だから性能のために意図的に崩す（非正規化）。ただし崩すには条件がある。

  1. 書き込み経路が1つ — カウンタを更新するのはトリガーかRPCだけ。アプリの各画面から update しない
  2. 再計算できる — 元データ（match_record）から users.trophy を再構築できる
  3. ズレを検知できる — 定期的に突き合わせるクエリがある

この3つが言えない非正規化は、単なるバグの温床。面接では「なぜ崩したか」と「どう守っているか」をセットで言う。

面接での答え方（正規化を聞かれたら）

「正規化は更新時の矛盾を防ぐための分解で、1つの事実を1箇所に置くのが原則です。ただ実務では読み取り性能のために意図的に非正規化するので、書き込み経路を1つに限定する・元データから再計算できる・ズレを検知できる、この3つを満たすときだけ崩しています。」

「このアプリだと users.trophy がそれで、元は match_record を集計すれば出せますが、ランキング表示のたびに集計したくないので列として持たせて、更新はトリガーとRPCに閉じています。」

02データベース設計の基本

テーブルを書き始める前に決めること。ここを飛ばすと後でテーブルを作り直すことになる。

決める順番

  1. エンティティを名詞で洗い出すユーザー、部屋、対戦結果、メッセージ、募集。動詞（参加する・承認する）は状態か中間テーブルになる。
  2. 各エンティティの「寿命」を分ける進行中（頻繁に更新され、短命）／確定（追記のみ、不変）／ログ（監査用）。寿命が違うものは同じテーブルに入れない。
  3. 関係のカーディナリティを決める1対多ならFKを多側に。多対多は中間テーブル。1対1は「分ける理由」があるときだけ。
  4. キーを決める代理キー（uuid/連番）を主キーにし、業務上の一意性は別途UNIQUEで守る。公開IDは推測されない値にする。
  5. 制約を書くNOT NULL / FK / UNIQUE / CHECK。ここを書かないと、不正なデータは必ず入る。
  6. 主要クエリを先に書くどの画面がどの条件で何を並べて読むかを先に決め、そこからインデックスを逆算する。
  7. 認可を決める誰がどの行を読める／書けるか。アプリ側のifではなくDBのポリシーで表現できる形にする。

制約の効き方

制約守れること書かないと
NOT NULL必須項目NULLが混ざり、クライアント側に ?? が増える
FOREIGN KEY参照先が存在する削除済みユーザーを指す孤児行が残る
UNIQUE二重登録の防止同じ人が同じ募集に2回応募できる
CHECK値の範囲・列間の関係player1_id = player2_id の部屋が作れる

インデックスの考え方

インデックスは「クエリの形」に対して貼る。迷ったら複合インデックスの列順は「等値条件 → 並べ替え列」。

-- 一覧クエリ: ある部屋のメッセージを新しい順に20件
select * from open_chat_messages
 where room_id = $1 order by created_at desc limit 20;

-- これに対応するインデックス（等値 → ソート列）
create index idx_open_chat_messages_room_created
  on open_chat_messages (room_id, created_at desc);

FK列だけのインデックスでは「絞り込み」は速くなるが「並べ替え」は残る。複合にするとソートが消える。

迷ったときの判断基準

問い判断
同じ事実が2箇所にある？片方を消す。性能上必要なら「更新経路を1つに」して残す
この列、どこからも読まれていない？消す。将来使うかも、で残すと永久に残る
状態をbooleanで持っている？日時（matched_at）にできないか検討。booleanは「いつ」を失う
文字列で状態を持つ？CHECK か ENUM を付ける。付けないとタイポが入る
複数テーブルを同時に更新する？1トランザクション（RPC）に閉じる。クライアントの呼び順に依存させない

04面接での話し方

AIに書かせたことは隠さない。評価されるのは「判断を説明できるか」と「出力を検証できるか」。

30秒版

「設計で軸にしているのは、状態を寿命で分けることと、整合性をクライアントに持たせないことです。進行中の対戦・確定した結果・監査ログを別テーブルに分け、複数テーブルにまたがる更新はRPCで1トランザクションに閉じ、認可はRLSでテーブル単位に定義しています。AIはその方針を渡して雛形を書かせるのに使い、生成物は制約と実行計画で検証して直しています。」

90秒版（深掘りされたとき）

「まず状態を寿命で3層に分けています。進行中の対戦は更新が頻繁で短命なので rooms_v3、確定した結果は追記だけで不変なので match_record、削除や通知は log テーブルです。同じテーブルに入れると、更新のたびに履歴側の整合性を気にする必要が出るためです。」

「次に整合性です。参加・承認のような複数テーブルを更新する操作は、クライアントから複数APIを叩かせると途中で失敗したときに中途半端な状態が残るので、security definer のRPCで1トランザクションに閉じています。権限はアプリのifではなくRLSで持たせていて、anon keyが漏れても他人のDMは読めない形にしています。」

「読みの性能は非正規化で確保しています。戦績は元データから集計できますが、一覧のたびに集計したくないので users にカウンタとして持たせて、更新経路はトリガー1箇所に限定しています。」

「AIの使い方ですが、設計判断は自分で決めて、それを制約としてプロンプトに明示しています。生成されたDDLは、制約が入っているか・RLSを別ユーザーで叩いて期待通りか・一覧クエリが EXPLAIN ANALYZE でインデックスを使っているか、を確認して直しています。」

言い方の変換表

そのまま言うと弱いこう言う
AIに作ってもらいました方針と制約を自分で決め、AIにドラフトを書かせて検証しています
正規化しましたどこを正規化し、どこを性能のために崩したか、崩した分をどう守っているか
RLSを入れました誰がどの行を読めるかをポリシーで表現し、別ユーザーで検証した
インデックスを貼りましたこの一覧クエリに対してこの列順で貼り、実行計画でソートが消えたことを確認した
関数にまとめました複数テーブル更新の原子性を保つため、1トランザクションに閉じた
注意

上のスクリプトは、実際にやったことにしか使わない。特に「EXPLAINを見た」「別ユーザーでRLSを確認した」は、聞かれた瞬間に詳細を突かれる。今日1回ずつ実行しておけば、そのまま事実として言える。

05悪いところ

migrationを読んだ結果の指摘。上から直す。[INFERENCE] は本番DBで要確認。

重大 / セキュリティ

1. レガシー7テーブルが USING (true) のまま

users, rooms, rooms_v2, rooms_v3, messages, match_record, transfer に、全操作を許可するポリシーが残っている。

CREATE POLICY "Allow all access for anon and authenticated"
  ON "public"."users" TO "authenticated", "anon"
  USING (true) WITH CHECK (true);

これがあると、anon keyだけで他人の trophy/win/lose を書き換えられる。ランキングが成立しない。メッセージの改ざん・削除も同じ。RLSを有効にしていても、このポリシーがOR条件で全部通すので意味がない。

修正: DROP POLICY して本人限定のポリシーに置き換える。まず guides ではなく pg_policies を本番で確認して、残っているものを列挙する。

重大 / セキュリティ

2. ポリシー置換の条件が逆

IF EXISTS (SELECT 1 FROM pg_policies
           WHERE tablename='users'
             AND policyname='Users can update their own data')
THEN
  DROP POLICY ...; CREATE POLICY ...;
END IF;

「存在したら作る」になっているので、ポリシーが無い状態では何も作られない。IF NOT EXISTS か、DROP POLICY IF EXISTS してから無条件に作る。

高 / 設計

3. rooms / rooms_v2 / rooms_v3 の三重化

3つがほぼ同一の列構成（player1_id, player2_id, is_matched, current_theme, used_theme_ids …）。しかも messages.room_id はどれを指すか不明。同じ事実が3箇所にある、正規化の逆。

「v2に上げた」ではなく旧テーブルを消していないだけ。データ移行してビューかリネームで1本にすべき。面接では「段階リリースの名残で、今は移行対象」と正直に言うのが安全。

高 / 整合性

4. FKが無い列がある

  • rooms_v3.player1_id / player2_id — FKなし
  • messages.room_id — FKなし
  • match_record.roomid — 部屋へのFKなし（ユーザーへはあり）

ユーザーを消しても部屋は残り、存在しない部屋を指すメッセージも入る。孤児行は後から消せない（何が正しいか判断できない）。

中 / 一貫性

5. 同じ概念を別の型で表現している

概念roomsmatch_record問題
勝者rooms_v2.winner char(1)winner uuid片方は"1"/"2"、片方はユーザーID。変換が必要で事故る
選択player1_choice booleanplayer1_choice textboolとtextで意味が違う
マッチ成立is_matched boolean—「いつ」が消える。遅延計測もできない

同じ概念は1つの型・1つの表現に統一する。winner_user_id uuid に寄せる。is_matched は matched_at timestamptz に。

中 / 1NF

6. used_theme_ids integer[]

配列なので、重複を防げない・参照整合性がない・「このテーマを使った部屋」を索引で引けない。正規化するなら:

create table room_used_themes (
  room_id  uuid not null references rooms_v3(id) on delete cascade,
  theme_id integer not null references debate_themes(id),
  primary key (room_id, theme_id)   -- 重複をDBが拒否する
);
中 / 重複

7. 同じ事実が2箇所

users.is_notification_enabled と notification_settings.is_notification_enabled。users.fcm_token と通知設定。users.trophy と match_record の集計値。

1つ目は明確な重複。どちらかを消す。カウンタは「更新経路1つ」の条件付きで残す。

中 / 要確認 [INFERENCE]

8. brock_user.id にデフォルトが無い

"id" bigint NOT NULL,   -- nextval / identity なし

一方 debate_themes.id にはシーケンスが付いているので、dumpの取りこぼしではない可能性が高い。アプリは id を指定せずに insert している:

await supabase.from('brock_user').insert({
  'user_id': myId, 'block_user_id': targetUserId,
});

この場合 null value in column "id" violates not-null constraint でブロック機能が毎回失敗する。本番で \d brock_user を確認する。直すなら:

create sequence if not exists brock_user_id_seq;
alter table brock_user alter column id set default nextval('brock_user_id_seq');
-- もしくは id を uuid default gen_random_uuid() に統一
中 / 構造

9. ロジックがRPC 80本に集中

原子性は担保できるが、SQLの関数はテストしづらく、差分レビューもしにくい。1本が200行を超えると、もはやmigrationのレビューでは追えない。

目安: 「原子性が必要」「RLSだけでは表現できない」ものだけRPCに残し、それ以外のドメインロジックはアプリ側へ。少なくとも純粋な計算はSQLに置かない。

低 / 命名

10. 命名の揺れ

現状あるべき
brock_userblocked_users（typo + 単数形）
match_record.roomidroom_id
debate_themes_request のPKが theme text代理キー + UNIQUE(theme)
テーブル名の単複混在（users / messages / app_config）複数形に統一

命名は後から直すのが一番高い。だから面接でも「次に作るときは先に規約を決める」と言える。

06改善の順番

全部やると終わらない。影響が大きく、戻せるものから。

  1. レガシーテーブルの全許可ポリシーを落とす セキュリティなので最優先。新しいmigrationで DROP POLICY → 本人限定のポリシーに置換。適用前に pg_policies で現状を列挙する。
  2. ポリシー置換の条件を直す IF EXISTS の反転を修正。既存のmigrationは書き換えず、修正用の新しいmigrationを足す（適用済みの履歴は変えない）。
  3. brock_user.id のデフォルトを確認・修正 ブロック機能が動いていない可能性があるので、機能の生死を先に確認。
  4. FKを足す rooms_v3.player1_id/player2_id、messages.room_id。既存の孤児行を先に洗い出してから ALTER TABLE ... ADD CONSTRAINT。ON DELETE は業務で決める（履歴を残すなら SET NULL）。
  5. 型と表現の統一 winner を uuid に、is_matched を matched_at に。アプリ側の読み替えを1箇所に集約してから移行。
  6. used_theme_ids を中間テーブルへ データ移行 → アプリ移行 → 列削除。3ステップに分けると戻せる。
  7. rooms 系を1本に統合 一番大きい。ビューで吸収してから実テーブルを畳む。
面接での言い方

「今の構造には技術的負債があって、レガシーテーブルに全許可のRLSが残っているのは最優先で直すべき点です。すでにFKの欠如とroomsの三重化も把握していて、影響の大きい順にmigrationを分けて直す計画を持っています。」

弱点を自分から言える人は、設計を理解している人と見なされる。隠すより強い。
