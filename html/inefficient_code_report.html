① FCMプッシュ通知の直列 `await` ループ処理（タイムアウト・遅延の主因）

supabase/functions/notify_trigger/index.ts:221

オープンチャットやグループDMへのメッセージ投稿時、送信対象ユーザー全員に対して for (const user of filteredUsers) で 1人ずつ直列に `await sendFcm(...)` しています。
対象者が20人いればGoogle認証・通知サーバーへのHTTP通信待ちが20回直列に発生し、Edge Functionが数秒フリーズしたりタイムアウトする重大なボトルネックです。

現状のコード（直列待ち・低速） 
// 1人ずつ順番に通信完了を待つ（人数分だけ遅延が増大）
for (const user of filteredUsers) {
  if (!user.fcm_token || uniqueTokens.has(user.fcm_token)) continue;
  uniqueTokens.add(user.fcm_token);
  const sent = await sendFcm(supabase, user.id, accessToken, user.fcm_token, ...);
  if (sent) successCount++;
}
改善策（Promise.allSettled による並行一斉送信） 
// 全員への送信を並行して一斉実行（全体の所要時間は1回分とほぼ同等に）
const sendPromises = Array.from(uniqueTokens).map(async (token) => {
  const user = filteredUsers.find(u => u.fcm_token === token);
  if (!user) return false;
  return sendFcm(supabase, user.id, accessToken, token, title, messageBody, type);
});
const results = await Promise.allSettled(sendPromises);

② `GamePage.dart` での毎秒画面全体リビルド（バトル中Jank・カクつきの主因）

lib/views/GamePage.dart:28-180

800行を超える巨大な GamePage のトップレベルで final countdown = useState<int?>(null); を保持し、毎秒のタイマーで countdown.value = diff; を代入しています。
これにより、1秒ごとにGamePage全体の全Widgetツリー（チャット一覧、ヘッダー、アニメーション等）が丸ごと再描画（Rebuild）され、メッセージ入力やスクロール時に激しいカクつきを引き起こしています。

現状（画面全体のルートWidgetでState更新） 
// GamePage.dart の build 内
final countdown = useState<int?>(null);

gametimer.value = Timer.periodic(const Duration(seconds: 1), (timer) {
  countdown.value = diff; // 👈 毎秒 GamePage 全体が再ビルドされる！
});
改善策（タイマー表示部分を独立した専用Widgetに切り出し） 
// カウントダウン表示専用の独立Widget（再描画はこの小さな部品の中だけ）
class CountdownTimerWidget extends HookWidget {
  final DateTime deadline;
  const CountdownTimerWidget({super.key, required this.deadline});

  @override
  Widget build(BuildContext context) {
    final remaining = useState(0);
    // タイマー更新はここだけにとどまる（GamePage本体は一切リビルドされない）
    return Text(formatTime(remaining.value));
  }
}
重要度: 中 Supabase SQL / RLS

③ RLSポリシーにおける `auth.uid()` の毎行再評価（フルスキャン化リスク）

supabase/migrations/20240000000000_remote_schema.sql

多くのRLS（Row Level Security）ポリシーで USING (user_id = auth.uid()) のように直接記述されています。
PostgreSQLの内部仕様により、auth.uid() を単体で書くとテーブル内の全行に対して毎行関数が再評価され、データ量が増加した際にインデックスが効かず全行Seq Scanが発生します。

❌ 修正前（行ごとに毎回関数評価）
CREATE POLICY "Users can update their own data"
  ON users FOR UPDATE 
  USING (id = auth.uid());
⭕ 修正後（SELECTで囲み1クエリ1回だけキャッシュ評価）
CREATE POLICY "Users can update their own data"
  ON users FOR UPDATE 
  USING (id = (SELECT auth.uid()));
重要度: 中 Supabase データベース設計

④ 頻出検索・ソート用「複合インデックス」の未作成（DBフルスキャン）

match_record / dm_messages / open_chat_messages

試合履歴（`match_record`）やチャットメッセージにおいて、player_id や room_id で絞り込んで created_at DESC でソートするクエリが主軸ですが、複合インデックスが存在しません。
そのため、全データをフルスキャンしてDBのCPUメモリ上で並び替え（Sort）を行う無駄な負荷が発生しています。

⚡ 追加すべき高速化インデックス（SQL）
-- 1. 試合履歴の検索・ソート爆速化
CREATE INDEX IF NOT EXISTS idx_match_record_p1_created ON public.match_record (player1_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_match_record_p2_created ON public.match_record (player2_id, created_at DESC);

-- 2. DM & オープンチャットメッセージの過去ログ取得高速化
CREATE INDEX IF NOT EXISTS idx_dm_messages_room_created ON public.dm_messages (room_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_open_chat_messages_room_created ON public.open_chat_messages (room_id, created_at DESC);

⑤ Google OAuthアクセストークンの毎リクエスト再取得（無駄なHTTP通信）

supabase/functions/notify_trigger/index.ts:367

プッシュ通知を発行するたびに getAccessToken() でGoogle認証サーバーへ新しいトークンを取りに行っています。
GoogleのOAuthトークンは1時間有効であるため、モジュールスコープ（関数の外側）のメモリにキャッシュすることで、2回目以降の通信待ち時間（200〜500ms）を0msに削減できます。

⭕ モジュールスコープを利用したメモリキャッシュ実装
// 関数の外側に保持（コンテナ生存中はずっと有効）
let cachedToken: string | null = null;
let tokenExpiresAt: number = 0;

async function getAccessToken(): Promise<string> {
  const now = Date.now();
  // 有効期限内（余裕を見て5分前まで）ならGoogleへ行かず即返却
  if (cachedToken && now < tokenExpiresAt - 5 * 60 * 1000) {
    return cachedToken; // ⚡ 通信0秒で即返却
  }
  // 期限切れ・初回のみ取得
  const token = await fetchNewToken();
  cachedToken = token;
  tokenExpiresAt = now + 3600 * 1000;
  return token;
}

⑥ 掲示板・対戦募集・オプチャ一覧の「全件一括取得」＆ 投稿・いいね時の全件再フェッチ

lib/provider/bbs_timeline_provider.dart:55

コミュニティ画面の各タブ（掲示板・対戦募集・オプチャ一覧）において、ページネーション（初期件数制限＋スクロール追加読み込み）がなく、最初から全件取得しています。
さらに掲示板では、投稿追加・削除・いいね失敗時に毎回 await fetchPosts() でリスト全体を全件再取得しているため、データ量が増えると大きなラグが発生します。

⑦ Supabase Realtime チャンネルの解放不備（リスナー重複・メモリリーク懸念）

lib/provider/dm_provider.dart:203

dm_provider.dart の `dispose()` 内で _channel?.unsubscribe(); のみが呼ばれています。
supabase_flutter の仕様上、supabase.removeChannel(_channel!) を明示的に呼ばないとクライアント内部のチャンネルマップに残り続け、画面を開閉するたびにチャンネルが蓄積します。

❌ 現状（マップに残る）
@override
void dispose() {
  _channel?.unsubscribe();
  super.dispose();
}
⭕ 改善後（完全に削除）
@override
void dispose() {
  if (_channel != null) {
    supabase.removeChannel(_channel!);
  }
  super.dispose();
}
重要度: 低 Flutter / 設計・初期化

⑧ `SharedPreferences.getInstance()` の各所での都度 await 呼出し

GamePage / history_provider / bbs_timeline_provider

各プロバイダーや画面内のメソッド内で個別に await SharedPreferences.getInstance() を呼び出しています。
main.dart でアプリ起動時に一度だけ取得し、Riverpod の Provider で DI（注入）して使い回すことで、非同期待ちのない同期アクセスが可能になりコードもシンプルになります。
