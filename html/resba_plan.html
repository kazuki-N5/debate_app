⚔️ レスバ機能 設計・要件定義書（コンテンツ融合型）

写真を添付する感覚で、コメント・ポスト・DMメッセージに「レスバ」を添付する 要件定義・UI設計・データベース設計

1. 概要・コンセプト

⚔️ レスバ（対戦招待）をコンテンツに添付
  • 返信にレスバをつける 新規
    • 返信に写真をつけるのと同じ操作で、返信に「レスバ」を添付して送信
    • コメント欄で口論になったら「レスバしようぜ」の流れに
  • ポストにレスバをつける 新規
    • ポスト作成時 or 既存ポストに「レスバ」を添付
    • 見た人が「⚔️ 応じる」→ 対戦成立
  • メッセージでレスバ（写真）を送る 新規
    • DMの入力欄で写真アイコンの隣の「⚔️」からレスバを送信
    • 相手に「レスバ」カードとして届き、承諾/拒否
  • 対戦募集タブ・募集中一覧は作らない 方針
    • 募集の独立UI（タブ・一覧・管理画面）は廃止し、チャット/コメントに融合
  • バトル実行は rooms_v2 を使用 既存
    • 承諾されたら既存の対戦フロー（rooms_v2）でバトル開始
💡 コンセプト：「レスバ」はコンテンツに添付するアタッチメントです（写真添付と同等の操作感）。 募集一覧・申込者一覧・参加人数のような「対戦募集システム」のUIは一切持たず、 会話の中で自然に「⚔️ レスバしようぜ」と誘える流れを作ります。

2. 体験フロー（シナリオ）

コメント欄で議論が白熱
二人が意見を交わす → 返信に「⚔️ レスバ」を添付
テーマを設定して送信 → 相手に届く
「⚔️ レスバが届きました」 → 承諾 バトル開始
rooms_v2 で二人が対戦
レスバなしの普通の返信 ⇄ 拒否 / 無視
会話はそのまま続く
  • 返信・DMは相手が最初から決まっているため、「相手に届いて承諾/拒否」のシンプルな1対1フロー。
  • ポストは誰でも応じられるフロー（応じた人を投稿者に1件ずつ表示 → 承認/拒否）。
  • 拒否されても普通の会話は継続。バトルはあくまで「レスバ」を承諾した時だけ始まる。

3. コンテンツ別の設計

3.1 返信にレスバをつける（コメント欄）

項目設計
導線返信入力欄のツールバーに [📷 写真] [⚔️ レスバ] を並べて配置。レスバアイコン → 添付シート（テーマ / 選択肢1 / 選択肢2）
相手返信先の相手（親コメントの投稿者 or ポスト投稿者）がそのまま対戦相手
相手側の表示返信スレッド内に「⚔️ ○○さんからレスバが届きました」カード（テーマ表示 + 承諾/拒否ボタン）
成立後承諾 → rooms_v2 でバトル開始。拒否 → カードに「拒否されました」と表示
補足レスバ付きの返信は本文の上に ⚔️ バッジ付きの添付表示（写真添付と同レイアウト）

3.2 ポストにレスバをつける

項目設計
導線ポスト作成画面に「⚔️ レスバを付ける」オプション。既存ポスト詳細にも「このポストにレスバを付ける」ボタン
相手不特定。ポストを見た誰でも「⚔️ 応じる」が可能（受付順に投稿者へ1件ずつ届く）
投稿者側の表示応じた人が来たら1件ずつ「⚔️ 誰かがレスバに応じました」と表示 → 承認/拒否（一覧・人数表示なし）
成立後承認 → rooms_v2 でバトル開始。他の応募は自動却下。拒否 → 次の応募者を表示
表示レスバ付きポストはカードに ⚔️ バッジ、詳細に「このポストにレスバが付いています」カード

3.3 DMでレスバ（写真）を送る

項目設計
導線DMの入力欄で [📷 写真] [⚔️ レスバ] を並べて配置。写真を送るのと同じ操作でレスバを送信
相手DMルームの相手（dm_room_members の他方）
相手側の表示メッセージとして「⚔️ ○○さんからレスバが届きました」カード（承諾/拒否）
成立後承諾 → rooms_v2 でバトル開始。拒否 → カードに「拒否されました」と表示
✅ 共通ルール：レスバ送信・応募は対戦中（rooms_v2 進行中）は不可。 応募（ポストへの「応じる」）は同時1件まで。相手待ちのレスバは送信者側でキャンセル可能。

4. 状態遷移・排他ルール

4.1 レスバ（battle_invites.status）

pending
提案中（相手待ち） → 承諾 accepted
バトル開始（rooms_v2） → バトル終了 finished
pending → declined
相手が拒否 ← cancelled
送信者が取り下げ
  • ポスト型は pending 中に応募を受け付け、承認された応募者で accepted へ。
  • 承諾でバトルが始まったら、送信者の他の pending レスバは自動 cancelled（対戦の二重化防止）。

4.2 ユーザーの対戦状態

フリー → レスバ提案中
相手の承諾待ち → 承諾 対戦中
rooms_v2 → 終了 フリー
⚠️ 排他ルール：
  • 対戦中（rooms_v2 進行中）は新たなレスバ送信・応募ができない。
  • ポストへの「応じる」は同時1件のみ（別のレスバに応募済みなら申請不可）。
  • DM・返信のレスバ（指名型）は複数送ってよいが、どれかが承諾されたら他は自動キャンセル。

6.3 rooms_v2 との関係（既存再利用）

battle_invites
status=pending → 承諾（指名型）/ 承認（post型） rooms_v2 を作成
player1=sender / player2=承諾者

  • ランダムマッチ（ホームの既存ボタン）は現行のまま残し、レスバ機能とは独立して動作。

6.4 RLS（行レベルセキュリティ）

種別SELECT 可視範囲書込
post 型全員（ポストの可視性に準ずる）送信は sender=自分 / 応募は applicant=自分（RPC 経由）
comment 型ポスト・コメントの可視性に準ずる送信は sender=自分 / 承諾・拒否は target_user=自分
dm 型DMルームの当事者2名のみ送信は sender=自分 / 承諾・拒否は target_user=自分
🔒 方針：書き込みはすべて RPC（SECURITY DEFINER）経由とし、テーブルへの直接書込は RLS で拒否。読み取りのみテーブル直参照（ポリシー）を許可。

10. 観戦機能（スペクテイター）設計・要件定義

参加型レスバ（オプチャ / 返信・ポスト / 対戦募集）のバトルを、それ以外のユーザーがリアルタイムで観戦できる機能。DM は1対1のプライベートのため観戦なし。

10.1 対象範囲と公開範囲

場所観戦公開範囲観戦導線
オプチャ内レスバ◯ルームメンバーのみルームのメッセージリスト上部「⚔️ ルーム内で対戦中」バナー
返信のレスバ◯全員（ポストの可視性に準ずる）返信スレッド内の「⚔️ 対戦中」表示
ポストのレスバ◯全員ポスト詳細の「⚔️ ライブ観戦」バナー
対戦募集（既存タブ）◯全員対戦募集タブの「対戦中（観戦可）」表示 / ホームの観戦バナー
DM✗—なし（観戦機能を提供しない）
💡 観戦はレスバ本体と同じ「コンテンツに付随」の思想。専用の観戦タブ・観戦一覧のような独立画面は作らず、 対戦中のコンテンツ（ポスト/返信/オプチャ/対戦募集カード）にバナーを付けて導線を提供します。

10.2 体験フロー

対戦中のバナーをタップ
ポスト詳細 / オプチャ / 対戦募集タブ → ライブ観戦
rooms_v2 を Realtime 購読（read-only） → バトル終了 結果発表
勝者・スコア・トロフィー変動 → 元のコンテンツへ戻る

10.3 リアルタイム同期（Supabase Realtime）

  • 観戦画面は rooms_v2 の postgres_changes を購読（channel：watch-{room_id}）。
  • 購読イベント：player1_choice / player2_choice（回答済み）、ラウンド進行、winner / result（結果）。
  • 観戦者数は battle_spectators の増減を購読して 👁 カウンターを更新。
  • 観戦画面は読み取り専用。参加者向けの操作（投票・発言・判定）は一切持たない。
  • 既存のバトル画面（GamePage 等）は変更せず、観戦用の read-only ビューを別途用意。

10.6 排他・エッジケース
