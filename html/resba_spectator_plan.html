👁️ レスバ観戦機能（スペクテイター）設計・要件定義書

参加型レスバ（ポスト / 返信 / オプチャ / 対戦募集）のバトルを、第三者（それ以外のユーザー）がリアルタイムで観戦できる機能の設計

1. 概要・コンセプト

💡 コンセプト：観戦はレスバ本体と同じ「コンテンツに付随するライブ」。 専用の観戦タブ・観戦一覧のような独立画面は作らず、対戦中のコンテンツ（ポスト詳細 / 返信スレッド / オプチャ / 対戦募集カード）に 「🔴 ⚔️ ライブ観戦」バナーを付けて導線を提供する。
項目設計方針
観戦対象レスバで始まったバトル（rooms_v2）
観戦者バトルに参加していないユーザー（第三者）
表示内容対戦者・テーマ・ラウンド経過・両者の回答状態・結果（読み取り専用）
リアルタイム性Supabase Realtime（rooms_v2 の postgres_changes 購読）
観戦者数👁 カウンター表示（battle_spectators + キャッシュ列）

2. 対象範囲と公開範囲

✅ 公開範囲の原則（確認済み方針）：
  • DM は当事者2名のプライベート → 観戦不可
  • オプチャ はクローズドなコミュニティ → ルームメンバーのみ観戦可
  • 掲示板（ポスト / 返信） は公開 → 全員観戦可
  • 対戦募集（既存タブ）は公開 → 全員観戦可（統合後）
場所観戦公開範囲エントリ導線備考
掲示板ポスト ◯ 全員 ポスト詳細の「⚔️ ライブ観戦」バナー バトル成立中のみ表示
返信コメント ◯ 全員 返信スレッド内の「⚔️ 対戦中」カード ポスト詳細に集約表示
オプチャ ◯ ルームメンバーのみ ルーム内「🔴 ⚔️ ルーム内で対戦中」バナー RLS で open_chat_members と照合
対戦募集（既存タブ） ◯ 全員 対戦募集タブの「対戦中（観戦可）」表示 新基盤（battle_invites）へ統合後
DM ✗ — なし（観戦機能を提供しない） 当事者2名のみ
ランダムマッチ ◯ 全員（ユーザー名・トロフィーが公開される点は認識合わせ） ホームの「👁 観戦できる対戦」一覧 ランダム発のバトルは battle_invites に紐付かないため、一覧導線をホームに設置。DM 発は除外
⚠️ 設計上の分離：観戦可否は「バトルがどこから始まったか」で決める。
  • レスバ発（post / comment / open_chat / bbs_tab）→ 観戦可（コンテンツにバナーを付随）
  • ランダム発（battle_invites に紐付かない rooms_v2 進行バトル）→ 観戦可（ホームに「👁 観戦できる対戦」一覧）
  • DM 発 → 観戦不可（battle_invites.attach_type='dm' を get_watchable_battles で除外）

3. 観戦の体験フロー

対戦中のバナーをタップ
ポスト / 返信 / オプチャ / 対戦募集タブ → ライブ観戦
rooms_v2 を Realtime 購読（read-only） → バトル終了 結果発表
勝者・スコア・トロフィー変動 → 元のコンテンツへ戻る
観戦レコードは自動削除

観戦者の状態遷移

フリー → 観戦開始 観戦中
read-only・いつでも退出可 → 退出 or バトル終了 フリー
✅ 観戦者は「対戦中」扱いにしない。観戦中でもレスバ送信・応募・ランダムマッチ参加は可能（読み取り専用のため）。 自分が参加中のバトルは観戦対象外（参加画面がそのまま表示される）。

制約・インデックス：

INDEX (battle_room_id) … 観戦者数カウント・一括退出

5.2 rooms_v2 への拡張（ALTER 1列のみ）

カラム型制約説明
spectator_countintNOT NULL DEFAULT 0観戦者数のキャッシュ（battle_spectators の INSERT / DELETE トリガーで更新）
⚙️ トリガー：battle_spectators の INSERT / DELETE → rooms_v2.spectator_count を加減算。 バトル終了時（winner 確定）は観戦者を一括 DELETE して 0 に戻す（または cron で掃除）。

5.3 公開範囲の RLS

対象RLS 設計
battle_spectators の INSERT RPC join_battle_spectator 経由のみ。公開範囲チェック（下記）をパスした場合のみ登録
観戦できるバトルの判定 RPC get_watchable_battles 内で判定：
attach_type = 'dm' は除外 ／ open_chat は自分がルームメンバーのみ ／ post・comment・bbs_tab は全員 ／ ランダム発（battle_invites に紐付かない進行バトル）はホーム一覧に含める

6. リアルタイム同期（Supabase Realtime）

項目設計
バトル状態の購読rooms_v2 の postgres_changes（channel: watch-{room_id}）。選択・ラウンド・結果をライブ反映
観戦者数battle_spectators の増減を購読して 👁 を更新
バトル終了winner 確定イベントで観戦画面 → 結果表示に切り替え、観戦レコードを一括削除
対象テーブルrooms_v2 / battle_spectators を supabase_realtime publication へ登録（冪等）
負荷対策観戦者数は COUNT でなく spectator_count キャッシュ列を参照（N+1・過負荷回避）

7. 排他制御・競合処理の設計（試合と募集）

✅ 設計方針：「対戦中かどうか」はサーバー（RPC）が必ず守る。クライアントはUXの確認ダイアログのみ。 常時監視（Realtimeでユーザー状態を追跡）はせず、操作したときに RPC が is_user_in_battle で判定する。
✅ 観戦者の扱い：観戦者は「対戦中」扱いにしない（is_user_in_battle の対象外）。観戦中でもレスバ送信・応募・ランダム参加は可能。 自分が参加中のバトルは観戦できない（参加画面が優先）。

7.1 「対戦中」判定の定義（共通）

項目内容
判定条件(player1_id = 自分 OR player2_id = 自分) AND player2_id IS NOT NULL AND winner IS NULL
対象外募集中（player2 未定）・応募待ち・マッチング待機・観戦中 は「対戦中」に含めない

7.2 シナリオ別の処理設計

#シナリオ設計（決定）実装箇所
1 応募中にランダムマッチ参加 許可する。試合中なら、後からホストが承認（承諾）しても RPC が応募者の is_user_in_battle で IN_BATTLE 却下するため二重試合は起きない。
※UX: ランダム開始時に「⚔️ 応募中のレスバを取り消しますか？」ダイアログ（任意・親切機能）		 HomePage / respond_resba・approve_post_resba
2 ホスト（募集中）のまま別の試合へ 許可する。対戦中はレスバの新規作成・応募・承諾が RPC でブロックされる。試合終了後に 保留中の応募を表示（承認→試合 / 却下） get_my_resba_status / ホームの保留バナー
3 対戦中に相手が承諾・承認 RPC が却下（IN_BATTLE）。承諾者（target）と送信者（ホスト）の両方を is_user_in_battle でチェック。どちらかが対戦中なら拒否 respond_resba / approve_post_resba（先行修正）
4 ポストで2個目のレスバ 作成は可能（複数提案OK）。上限は「送信者の pending レスバ数 ≥ 3 で RECRUITMENT_LIMIT_EXCEEDED」を RPC でチェック（未実装→P0 で追加）。
どれか1つが承諾されると他の pending は自動キャンセル		 create_post_resba（先行修正）
5 応募中に別のレスバへ応募 拒否（ALREADY_APPLYING）。RPC チェック + 部分ユニークインデックスで DB レベルでも保証 apply_post_resba（実装済み）
6 承諾・承認された瞬間 送信者の他 pending 提案を自動キャンセル、承諾者の保留応募も自動キャンセル（対戦の二重化防止） respond_resba / approve_post_resba（実装済み）
7 ランダム待機中に再度ランダム 既存の join_room_v2 は自分の待機ルームを考慮せず2個目を作る問題あり。P0 で「自分の player2 IS NULL ルームがあれば既存ルームへ参加 or ブロック」を検討（rooms_v2 のゴミ対策） join_room_v2（既存・要修正）

7.3 RPC で is_user_in_battle をチェックする箇所（一覧）

RPC誰をチェック状態

apply_post_resba応募者実装済み

7.4 エラーコードとフロントの挙動

コード意味フロントの挙動
IN_BATTLE自分（または相手）が対戦中「⚔️ 対戦中のため承諾/送信できません」を表示。承諾側のカードは「相手が対戦中」表示に変わる（応募は pending のまま残し、相手の試合終了後にホームで「保留中の応募」として表示）
ALREADY_APPLYING応募中のレスバがある現在の応募状態を表示しキャンセル導線を提示
RECRUITMENT_LIMIT_EXCEEDEDpending レスバが上限（3件）「募集中のレスバが上限です」を表示

8. エッジケース

ケース挙動
自分が参加中のバトル観戦対象外（参加画面がそのまま表示される）
対戦中の新規観戦可能（バトル開始後〜winner 確定前のみ join 可）
バトル終了観戦画面が結果表示へ切り替わり、観戦者レコードを一括削除

観戦中のユーザーread-only なのでレスバ送信・応募・ランダム参加は制限しない（「対戦中」状態に含めない）
