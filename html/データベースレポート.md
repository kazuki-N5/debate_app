## 重大度: HIGH（修正必須）

### H-1. mark_dm_room_read にメンバーシップチェックが無い（SECURITY DEFINER の権限昇格）
- 該当箇所: `sql/message_tab.sql` L204-212
- 理由: SECURITY DEFINER（オーナー=postgres、RLS バイパス）で、条件は `room_id = p_room_id AND sender_id <> auth.uid()` のみ。**任意の authenticated ユーザーが room_id を指定して呼ぶと、参加していないルームの他人の未読フラグを消せる**。既存の `is_dm_room_member()`（20260817102000 で定義済み）で防げる。
- 修正提案:
```sql
CREATE OR REPLACE FUNCTION public.mark_dm_room_read(p_room_id UUID)
RETURNS void LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$
BEGIN
    IF NOT public.is_dm_room_member(p_room_id) THEN
        RAISE EXCEPTION 'Not a member of this room';
    END IF;
    UPDATE public.dm_messages
    SET is_read = true
    WHERE room_id = p_room_id AND sender_id <> auth.uid() AND is_read = false;
END $$;
```
- 補足: dm_messages には UPDATE ポリシーが無い（SELECT/INSERT のみ）が、SECURITY DEFINER + 関数オーナー=postgres（=テーブルオーナー）により RLS はバイパスされ機能する。ただし「無条件に更新できる」状態なので関数内ガードが必須。

### H-2. notifications が supabase_realtime パブリケーションに未登録 → リアルタイム通知が機能しない
- 該当箇所: SQL全体（登録文が無い）
- 理由: `notification_provider.dart` は Realtime（onPostgresChanges）で通知を購読しているが、パブリケーションには `messages / rooms / rooms_v2 / rooms_v3 / dm_messages` しか無い（remote_schema L1562-1574、DMマイグレーション L109）。**未登録だと INSERT イベントが配送されず、通知バッジが更新されない**。
- 修正提案（冪等）:
```sql
DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM pg_publication_tables
    WHERE pubname = 'supabase_realtime' AND schemaname = 'public' AND tablename = 'notifications'
  ) THEN
    ALTER PUBLICATION supabase_realtime ADD TABLE public.notifications;
  END IF;
END $$;
```

## 重大度: MEDIUM（修正推奨）

- **M-1. dm_messages(room_id) にインデックスが無い**
  → `mark_dm_room_read` / 受信ボックスの最新取得・未読カウントが全件スキャン。
  `CREATE INDEX ... ON public.dm_messages (room_id, created_at DESC);` と部分インデックス `(room_id) WHERE is_read = false` を追加推奨。
- **M-2. chat_inbox_provider の N+1**（L53-115）
  → DMルームごとに ①メンバー取得 ②相手ユーザー取得 ③最新メッセージ ④未読カウント を for ループ内で逐次実行（ルーム数×4 ラウンドトリップ）。未読カウントは未読IDを全件取得して length。一括取得用 RPC（get_dm_inbox 等）の追加を提案。
- **M-3. 通知トリガーが users.is_notification_enabled を無視**
  → users モデルに存在する通知設定（ON/OFF）がトリガーに反映されず、OFF のユーザーにも通知が溜まる。仕様確認が必要。
- **M-4. user_follows の SELECT USING(true) は anon 含む全員にフォロー関係を公開**
  → bbs 系が全公開なのでプロジェクト方針とは一貫するが、フォローは個人関係の情報。非公開にするなら `auth.role() = 'authenticated'` に限定。

## 重大度: LOW（軽微・改善提案）

- **L-1.** コメント「is_read カラムが無い環境向けに追加」は誤り（実テーブルに既に存在。`ADD COLUMN IF NOT EXISTS` は no-op で安全だが誤解を招く）
- **L-2.** SECURITY DEFINER 関数に `SET search_path` が無い（完全修飾なので実害低、防御として推奨）
- **L-3.** `notifications_update_own` に WITH CHECK が無い（user_id 書き換えはブロックされるが、自分宛て通知の内容改ざん余地あり）

## 問題なし（確認済み項目）

- **FK制約名の一致**: 全FKが inline 定義で、デフォルト命名規則により `notifications_actor_id_fkey` / `notifications_post_id_fkey` / `notifications_comment_id_fkey` が生成され、`notification_provider.dart` の依存と完全一致。型は全て UUID→UUID。✓
- **REVOKE INSERT, DELETE の影響**: トリガーは SECURITY DEFINER（postgres=テーブルオーナー）で REVOKE 対象外かつ RLS バイパス。通知生成は正常動作。service_role も影響なし。✓
- **重複防止・いいね解除時の削除・返信条件**: `bbs_likes` / `bbs_comment_likes` に UNIQUE 制約があり DB レベルで重複防止済み。DELETE トリガーと FK CASCADE で二重に安全。✓
- **エッジケース**: 自己いいね/返信/フォローは全トリガーでガード、`follower_id <> followed_id` の CHECK あり。削除済みポストへのいいねは FK 違反で遮断。`auth.uid()` NULL 時は no-op で安全。✓
- **通知の漏えい**: SELECT は自分宛てのみ。JOIN 先（users / bbs_posts / bbs_comments）は既存 RLS で全公開のため新規漏えいなし。✓
- **再実行安全性**: `IF NOT EXISTS` / `DROP POLICY IF EXISTS` / `DROP TRIGGER IF EXISTS` / `CREATE OR REPLACE` / 冪等な REVOKE が網羅。唯一の非冪等リスクは H-2 のパブリケーション登録（修正案は DO ブロックで冪等化済み）。✓

### 通知の取り消し仕様（追記）
- **いいね・コメントいいねの解除トリガー**（`remove_bbs_post_like_notification` / `remove_bbs_comment_like_notification`）は**削除** → 解除しても通知は履歴として残る（X/Twitter方式）
- **フォロー解除トリガー**（`remove_follow_notification`）は**残す** → フォロー解除で通知は消える
- 重複防止の `DELETE→INSERT`（再いいねで1件に最新化）は全て残っている

### 注意
- v1 を実行済みの場合も、v2 をそのまま再実行すれば上書きされます（冪等設計）
- すでに v2 を実行済みで、いいね・返信の削除トリガーだけ外したい場合は以下を実行してください:
```sql
DROP TRIGGER IF EXISTS trg_remove_bbs_post_like_notification ON public.bbs_likes;
DROP FUNCTION IF EXISTS public.remove_bbs_post_like_notification();
DROP TRIGGER IF EXISTS trg_remove_bbs_comment_like_notification ON public.bbs_comment_likes;
DROP FUNCTION IF EXISTS public.remove_bbs_comment_like_notification();
```
- RPC 実行時に `get_dm_inbox` 等が見つからない場合は、SQL v2 がまだ実行されていないためです

## 付録: より効率的な構造の提案（未実装・検討用）

### E-1. DM既読管理を「メッセージ単位 is_read」→「メンバー単位 last_read_at」に変更（LINE方式）
現在: 各 dm_messages 行に is_read フラグ → 既読化のたびに該当ルームの未読行を複数 UPDATE、未読カウントも毎回スキャン。
改善: `dm_room_members` に `last_read_at`（または last_read_message_id）を追加。
- 既読化 = 自分のメンバー行1行を UPDATE（`dm_room_members` は1ルーム2行なので超軽量）
- 未読数 = `created_at > last_read_at` のメッセージを COUNT（インデックスがあれば高速）
- オプチャも同様に `open_chat_members.last_read_message_id` で対応可能

### E-2. メッセージ一覧の N+1 解消（一括取得 RPC）
現在: chat_inbox_provider がルーム数×4 クエリを逐次実行。
改善: `get_dm_inbox(p_user_id)` / `get_open_chat_inbox(p_user_id)` のような RPC を1本用意し、ルーム・相手・最新メッセージ・未読数を1クエリ（サブクエリ+GROUP BY）で返す。

### E-3. インデックス追加
`dm_messages (room_id, created_at DESC)` と部分インデックス `(room_id) WHERE is_read = false`。通知側は既存の `(user_id, created_at DESC)` で十分。

### E-4. 通知一覧のページネーション
現在は `limit(100)` 固定。カーソル方式（created_at < 最終取得時刻）にすると長期利用時の一覧取得コストが下がる。

### E-5. 通知の集約表示（任意・高度）
「Aさんと他2人がいいねしました」のような集約表示。実装コストが高いため、件数が増えてから検討でよい。
